# Review of the original implementation

Reviewed baseline: `4cd4d8b629cd15d02c41f634ad3ac6a910bf6dae` (the original `main` commit).

The design describes a useful architecture: one computer runs the logic, and reusable clients bridge displays, redstone and sensors. The original repository contains a partly written OS, one non-working IO client, and standalone archived programs. The written design describes considerably more than the original code implements.

## Defects preventing the first IO connection

| Original code | Effect | Repair |
| --- | --- | --- |
| OS listens on `100`; IO client uses `45231` | They cannot receive each other's packets | Shared configuration and transport |
| `local modem` exists only inside each `mainLoop` | Helper functions see a nonexistent global `modem` | Transport object passed explicitly |
| OS calls `modem.send` | Raw modems expose `transmit`, not `send` | One shared transmit implementation |
| Table sent directly to an old modem API | Compatibility depends on the installed CC version | Serialize every wire packet to a string |
| Server assumes its modem is on `back` | A different placement fails | Detect/recover a modem on any side |
| IO client announces once and has no welcome handling | No confirmed connection or recovery if OS starts later | Nonce-echoed welcome and periodic announcements |
| `sleep` after handling events | ComputerCraft's filtered sleep consumes unrelated events | Timer-driven unfiltered event loops; parallel console |

The modem API signature and event arguments are documented in the [ComputerCraft modem API](https://computercraft.info/wiki/Modem_(API)); the event-discarding behavior is documented in [os.pullEvent](https://computercraft.info/wiki/Os.pullEvent). String payloads also avoid relying on newer modem table support (see the [historical 1.5 channel tutorial](https://ccf.squiddev.cc/forums2/index.php?/topic/10343-15-modems-and-channels/)).

## Other broken behavior

- IO capability discovery checked attached peripherals for redstone methods. Bundled redstone belongs to the computer's `redstone` API, not to a cable peripheral.
- `readInputs` was never called. The event loop filtered out redstone events, and the OS had no input handler.
- The old OFF calculation OR-ed the current mask with an inverted colour mask. This could turn unrelated wires ON. The repaired OS computes a complete desired mask from logical boolean outputs; the client applies it directly.
- Output commands confused the client address (`io_main`) with the physical address (`left:16384`). These are now separate fields in OS-owned mappings.
- All commands used a shared channel with no recipient filtering. Packets now carry protocol, household network ID and recipient computer/client IDs.
- `sendToIO` and `handleTaskbarTouch` were referenced before their local declarations, resolving to nonexistent globals. Both paths are now real methods in the server module.
- `p5` was passed without being captured from `os.pullEvent`. Event fields are now captured deliberately; unused distance is not required by routing.
- The OS trusted `message.type` on arbitrary public-server traffic. Both transport and message handlers now validate their inputs.
- Sensor packets could overwrite arbitrary top-level state, including `windows`, via `state[message.varName]`. Raw sensor values now live under their registered sensor client; only typed `playerOnline` and `gameTime` update system indicators.
- Save directories were not created, file-open failures were unchecked, and only windows/registry were saved. Checkpoints now include app state, logical mappings/outputs and boot generations, with recovery and visible failures.
- Restored windows could be overwritten because `nextWindowId` reset to 1. IDs are now derived from restored windows.
- Rendering ignored window coordinates, failed to clip to the screen, and had an incorrect title/close-button width. Touch offsets did not match rendered content. Central composition and hit testing now share the same geometry.
- The taskbar handler was empty. There was no app API for opening windows or generic monitor client. A launcher, window controls, app lifecycle/API and generic monitor client now support the architecture. Apps are user-specific and opt-in; no app is bundled or enabled by default. The original switchboard used to exercise window/IO behavior remains a test fixture. The optional user Switchboard is now implemented separately as `apps_switchboard.lua`.
- Background jobs and saves depended on the arrival/count of unrelated events. Dedicated timers now drive background elapsed time and checkpoint intervals.

## Design decisions that need to remain explicit

1. **Saved intent versus observed hardware:** ON means the OS's desired state; confirmed means the IO computer applied it. External machine feedback requires a real input/sensor.
2. **Connection loss:** default clients switch outputs OFF after a 15-second timeout and restore saved intent on reconnect. This policy is configurable; it is transport behavior, not farm logic.
3. **Durability:** all app data and window layouts checkpoint every second; important counters/transitions checkpoint immediately. Coffee saves its active phase and remaining duration, with no downtime catch-up. Checkpoints are not an exact transaction with an external machine, so the repair does not claim to recover unsaved sub-second elapsed time or prove a physical harvest happened exactly once.
4. **App/view sizing:** actual character capacity from `monitor.getSize()` is authoritative for fit checks. A physical `5x4` classification requires separate metadata if still useful; it cannot safely be inferred from arbitrary text scale/resolution.
5. **Desktop ergonomics:** the coloured bottom taskbar and top-right controls offer two-step graphical grid/position selection through 3×3, two-corner custom sizing and coarse placement with one-cell move arrows that disappear at boundaries. Resize and Move remain on the first level. The title stays at the left on contrasting neutral chrome. OS settings is in Start; app accents use a shared palette. The console controls remain available.
6. **Public-server trust:** packet IDs and a pinned OS ID filter accidental traffic. They are not cryptographic authentication. Wireless sniffing/spoofing remains possible.
7. **App state:** all views share app data; normal apps run until their last view closes, while declared services such as Coffee keep running with zero views. All app hooks run centrally, must return promptly without sleeping/yielding, and should store serializable data only.
8. **Settings UI:** menus/drafts are per window; applied configuration is persistent shared app state. The OS's reusable IO picker supplies client, side and Digital/bundled-colour choices. Output binding can checkpoint an initial OFF intent atomically with the mapping.
9. **Clock:** the earlier implementation waited for a sensor even though ComputerCraft's built-in `os.time()` exposes Minecraft time. The taskbar now uses that API and retains sensor fallback when it is unavailable.

## Validation limits

The Lua 5.1 test harness executes the real server, IO, monitor, sensor and relay entry points against simulated APIs, including string-only modems and independent event queues/filesystems. Its radio model uses three-dimensional distance and configurable range/dimension. It does not emulate the Minecraft world, Java/TLS support, actual server range/weather/configuration or native mod-specific sensor behavior. Follow the README's one-wire test on the actual server before attaching production automation.

After the in-game UI report, tests now record actual foreground/background writes, reorder frames, replay/burst touches, drop render replies, exercise paging across announcements and suspend native drawing while a touch arrives. These reproduce missing transport/input safeguards and verify the new buffer/revision checks; they do not prove which condition caused every observed in-game click. A guided calibration test also runs the real monitor entry point, saves an offset and verifies corrected coordinates after reboot. Physical hitbox alignment on the user's monitor still needs in-game measurement.

The subsequent calibration screenshot showed the old exact-match check exiting on a differing second tap. Bundled-v11 collects three samples and tolerates at most one cell of residual per axis around their median, keeping the ±3-cell correction limit. Tests cover the second differing tap reaching target three, ignored old-target repeats, Retry after disagreement, Cancel without replacing the previous offset, and failed-save recovery. Native expected/received coordinates are printed for further diagnosis.

Bundled-v12 expands calibration to nine circle targets, prints diagnostic averages and per-axis agreement, and proposes zero on axes without 7/9 agreement. Tests cover a 5/4 split between zero and minus one being flagged without forcing a full-cell correction, preview markers moving onto intended targets, manual arrow adjustments, on-screen Reset requiring Save, direct stock reset preserving other monitor offsets, and cancellation/save-failure recovery. Touch events lack fractional character positions, so more samples improve confidence but cannot provide true half-cell correction. Colour tests change borders/taskbars across multiple monitors, verify readable foregrounds, save/reboot recovery, invalid-preference defaults and failed-save rollback. Coffee, window geometry and taskbar positioning remain unchanged.

Console tests execute the real main OS with cursor-recording terminals: connection logs arrive while editing a command in its middle, long drafts survive resizing, editing/history preserve drafts, clear keeps Coffee/window/output state and networking active, and quit saves and returns a clean cursor. The new editor reserves the bottom row instead of sharing a `read()` cursor with asynchronous messages. These checks run against simulated CC APIs, not the live Minecraft server.

Appearance/navigation tests run the real Start → OS settings → palette flow without enabling user apps, recover appearance and settings windows after reboot, roll back failed cosmetic saves, click diagram panes below their first row, and exercise move arrows/Place/OK at every boundary. A matrix of 512 Coffee page/size combinations checks row/style bounds, non-overlapping controls, unique menu paths and parent Back/Cancel navigation, including three-digit hours in the graphical clock. Another matrix checks 420 monitor/grid combinations and every popup page; 3×3 panes cover odd-sized workspaces exactly and restore across resolution changes/reboots. A raster check verifies swapped clock colours, unchanged double-size pixels and clearing old digit shapes through the real bridge. The user confirmed that the earlier countdown was correct; the clock change is visual only. This does not substitute for an in-game visual/input check.

After an in-game screenshot exposed the public server's `[IDT-Fix]` 0.5-second redstone limit, the harness gained a shared per-port write cooldown that reproduces that startup failure. IO now skips unchanged writes and queues changes with a default 0.6-second interval, acknowledging only fully applied snapshots. This tests the observed rule, not the complete server modification.

## Optional Switchboard (bundled-v13)

The original standalone switchboard provides the bundled-output concept only. `apps_switchboard.lua` implements saved view cards, all-colour side presets, custom 1–16 by 1–16 grids, paged switch tiles, per-switch routing and touch names, per-view management and app colours/density. The OS gains an additive batch routing API: mappings, removals, desired states and caller app data share a checkpoint before hardware sync. Wire conflicts or failed saves roll back the complete edit. Released wires remain in managed-side snapshots for clearing; the existing IO cooldown is untouched.

Switchboard tests use real monitor touches and independent clients for presets, custom cross-client/Digital routes, pending/offline intent, last-window close, restart recovery, unchanged/new routes, conflict with Coffee, failed creation/toggle/rerouting/deletion, grid shrink/grow, non-reused IDs, scoped All OFF, view order, both keyboard sizes and shared settings. A 588-case page/size matrix checks content bounds and disjoint hit rectangles. The installer test decodes the actual app through a simulated GitHub API response and boots it using only extracted core files. These tests and inspected colour renders are simulated; live Minecraft graphics, wireless behaviour and touch variability still require in-game use. Calibration is retained without changes as requested.

## Shared wires and colour previews (bundled-v14)

The user's correction supersedes v13's wire exclusivity: duplicate physical routes are allowed and share one desired value. Setting any reference updates every copy atomically, including other apps. A newly attached reference adopts the wire's current state; removing/rerouting one leaves surviving references alone. Only the final removal clears an unused wire. Batch `initialValue` distinguishes adopting a shared route from explicitly setting `value`. The saved schema remains compatible; legacy duplicate values normalize to their existing powered mask at boot. Snapshot-equivalent edits preserve the client's revision and acknowledgement.

The orange flash was reproduced: every periodic IO announcement cleared the whole client's ACK before repainting, although no output changed. Routine announcements now retain acknowledgement while still resending a health snapshot. Real reconnects, restarted counters and capability changes invalidate it. Tests inspect intermediate app repaints with health ACKs deliberately dropped, checking steady confirmation and no physical writes; actual unacknowledged output changes and IO restarts still show pending until ACK recovery. No IO-client or monitor update is needed.

Every Switchboard colour picker now stages selection before Apply/Cancel. UI colour, background, button border, unwired tile, active and inactive colours all appear in the same sample panel below the swatches at 24×15 content or larger. Tests cover each field's preview, staging/cancellation, Apply/reboot, exact fit boundary, small-screen controls, failed saves and old settings defaults. Active/inactive colours affect status strips; bundled fills retain wire identity. Coffee code, calibration, IO cooldown and desktop geometry are unchanged.

## Generic sensors and Reactor panel (bundled-v15)

The new sensor role supports OpenCCSensors' old queued `ocs_success`/`ocs_error` interface directly, plus immediate and yielding implementations. Calls are serialized, timed out and isolated from networking. Because old OCS queue IDs are per-peripheral and wrap, timed-out IDs are quarantined for that program session to prevent late results crossing sensor boundaries. Modem/sensor sides are detected automatically, and IC2, dedicated AE and other card names are reported without substituting inventory cards.

The hub assembles bounded, sequenced catalogs/readings under the correct client/side/target/session/boot identity. Partial catalogs do not replace complete target lists; multipart data stays isolated from OS state. Subscribers share one read. Compact unchanged heartbeats require the exact full base snapshot, so dropped changed data cannot make older data appear fresh. Full samples and catalogs repeat for recovery. Raw telemetry stays in memory and expires; saved configuration and manual output intent survive reset.

The supplied screenshot establishes the requested layout/data labels, not sensor availability. Old IC2 reactor fields supply heat, MaxHeat, Active and output. Melting is marked as derived when calculated at 85%; remaining time is unavailable unless supplied, with a Raw readings screen for server diagnosis. The optional Reactors app supports multiple targets per card/client and independently routed IO switches, shared references, rename, editing/deletion, small-screen paging and colour previews. Closing the last window stops detailed subscriptions while leaving manual switch intent intact.

Eighteen added tests bring the suite to 133 integration checks: multiple cards and reactor targets, dedicated AE discovery and multipart samples, native/direct/yielding reads, dropped catalog chunks/samples, card swaps/detach/restart, timeouts/late events, session validation and malformed data isolation, failed edits/commands, saved bindings/names/windows/switches, deduplicated targets, scoped deletion, close/reopen, stale touches after structural edits on another monitor, and sensor-role offline extraction/boot without the OCS Lua wrapper. A 560-case Reactor screen/size matrix checks row/style bounds and non-overlapping controls. These are simulated ComputerCraft Lua 5.1 checks; live Minecraft range, mod data, wiring and rendering remain to be verified.

## Chained wireless relays (bundled-v16)

The new relay role forwards the shared network transport for sensors, IO, monitors and other relays without changing their identities, sessions or app bindings. Relays and each original endpoint appear independently in the OS client list, with runtime observed paths and forwarding counts. There is no fixed software hop-count cutoff. Encoded packets and route metadata still have to fit ComputerCraft's physical wire limit.

Updated endpoints send direct and relay-channel copies with a persisted boot generation and increasing sequence ID. Copies are suppressed before handshake/application handling, so routine duplicated IO announcements cannot revoke earned ACK status or duplicate taps. Each relay appends itself to the visited path and rejects packets that have already visited it, preventing cycles independently of the bounded recent-packet cache. Path arrays, network/destination/reply identities and optional pinned server IDs are validated. Boot checkpoints stop networking on failed saves. Forwarding works before the relay's own welcome and resumes after modem reattachment. Old direct clients remain compatible; endpoints must update their network library to use relays.

Eighteen added tests bring the full suite to **151 integration checks**. They exercise the user's 120-block Y gap, 16- and 17-relay chains, separate OS listings, original IDs, actual sensor readings, commands/ACKs/inputs/touches, overlapping/direct paths, relay outages and alternate routes, OS/endpoint reboots and restored windows, cold start before the OS, lost welcomes/commands/ACKs, malformed/foreign/pinned traffic, large packets with long route IDs, modem reattachment, failed boot checkpoints and legacy/direct-only operation. Existing installer tests now install and boot all five roles offline and through the optional GitHub bootstrap. App sources, calibration, frame geometry and IO write scheduling remain unchanged. These are Lua 5.1 simulations; the live server's range, latency and rendering still need verification.

## Sensor side/catalog repair (bundled-v17)

The reported screenshot shows 62 local targets discovered before the sensor completes its OS connection. A matching failure was reproduced with five relays at a 30-block simulated range: one unnamed machine produced an empty catalog type, and the hub rejected the whole catalog. When that was the first catalog after connecting, the OS had no side to offer despite a healthy sensor handshake. This is a confirmed code failure matching the symptom; the user's actual target metadata has not yet been captured.

Native OCS 1.4.7 tile-target source supplies `Name`, `RawName` and `Position`. Names now fall back through nonempty display fields, raw identity and `Unknown`. The client retains raw identities; the hub preserves them and uses them to classify localized reactor names. The server also accepts blank/missing string types from older clients while continuing to reject invalid addresses and structured/oversized metadata. The selector explains waiting/rejected catalogs and exposes incompatible/error sides as disabled. The new `sensors [client]` console command reports protocol/boot, received cards/sides, target/reactor counts, partial catalogs and rejection reasons. Diagnostics stay outside saved OS/app state.

Six new checks bring the suite to **157 passing Lua 5.1 integration tests**: empty/localized names, legacy blank catalogs, rejection diagnostics and recovery, disabled/waiting picker states, incomplete-part diagnostics and the pre-discovered 62-target/five-relay reproduction with a real readout. Existing IC2 fixtures now use native Name/RawName fields. Update only OS and sensor roles for this repair; relay/network/IO/app/calibration/desktop code remains unchanged. Full Minecraft verification is still pending.
